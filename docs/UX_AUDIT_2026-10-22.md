# Claw Chaos — First-minute control UX audit (2026-10-22)

Baseline: `main` at `6ba0e900ec85721fa51aa369a817ca72aaa2b445`. Source-level review only; **no device screenshot or new automated test has been run**.

## Existing controls and what is already implemented

- `src/app/startApp.ts` creates `FirstPersonPlayerViewController`, `MobileCabinetControls`, `StaffCallControl`, and `CabinetRewardFeedback` for the playable cabinet. Avoid adding a duplicate control stack.
- `src/player/mobileCabinetControls.ts` provides a left virtual joystick and `DROP / CLOSE` touch button, including a 140 ms accepted-action debounce.
- `src/player/firstPersonPlayerView.ts` provides a contextual gaze/focus prompt and clears it during the temporary staff camera view. This is **not** a first-minute tutorial.
- `src/style.css` has separate portrait/landscape mobile control layouts, safe-area offsets, and a compact quality selector.

## Specific source-level UX defect

In `FirstPersonPlayerViewController.update()`, the `action === "primary"` branch unconditionally sets:

```ts
this.prompt.textContent = "[F] " + this.focus.target.label;
```

The same controller is created on touch-like devices. A touch-only player can therefore see a desktop keyboard shortcut even though the on-screen primary control is `DROP / CLOSE`. **Potential issue confirmed by source; reproduction on a real phone remains outstanding.**

### Recommended bounded implementation

1. Pass the existing `touchLike` selection from `startApp.ts` to the player-view prompt presentation, without changing physics input.
2. Desktop: retain the existing `[F]` prompt. Touch: render a short action label without keyboard prefix (or a touch-appropriate hint, subject to viewport review).
3. Preserve the current focused-target labels and clearing behavior during staff service.
4. Add a focused unit test covering desktop/touch prompt selection and a browser smoke check for both input modes.
5. Manually inspect portrait and landscape for overlapping the top-left CALL STAFF button or the prize/claw field; only adjust CSS if actually needed.

### Non-regression

Do not modify `primaryAction`, joystick vector mapping, accepted-action debounce, camera state, ChuteSensor, Rapier physics, prize mass, claw forces, staff service, or reward feedback.

## Follow-on onboarding concept (not yet implemented)

After the focused-prompt correction, a one-time dismissible, small-screen-safe control hint could explain: move claw; drag to look; DROP then optionally CLOSE; CALL STAFF. Avoid permanent overlays and duplicate text over existing controls. No claim of visual acceptance until a real-device check.
